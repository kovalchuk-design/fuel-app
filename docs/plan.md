# План: застосунок обліку пального (генерація 3 звітних документів)

## Context
Щомісяця вручну в Excel (.xls, декілька вкладок-місяців) складаються три пов'язані документи по в/ч А1446 (24 одиниці техніки: 17 авто, 1 ЗІЛ/ГАЗ тощо + генератори):
1. **Відомість заміру** — залишки пального в баках на дату (25-те), по авто × вид пального.
2. **Донесення (Додаток 17)** — зведення по кожному виду пального (л і кг): залишок на початок, прибуло, витрата по шляхових листах / робочих листах агрегатів, залишок на кінець; ще мастила й рідини (олива, ГТЖ, антифриз…).
3. **Розшифровка напрацювання техніки та витрати ПММ** — по кожному авто × виду пального: спідометр початок/кінець, залишок на початок, отримано, використано (= за нормою), залишок на кінець, економія.

Мета: ввести надходження від постачальника та шляхові листи → система рахує й генерує готові документи. Стек і підхід — як у dormitory-app (React+TS+Vite, HashRouter, Supabase, docxtemplater/pizzip, pdf-lib, docx-preview, vitest, Playwright, GitHub Actions → Pages), **але стилі — Tailwind** замість власного CSS.

## Рішення, прийняті з користувачем
- «Використано» = літри зі шляхового листа; норма не рахується (використано за нормою = фактично, економія = 0 за замовчуванням).
- Вихід: **усі три документи** у форматах **xlsx, docx, PDF**.
- 1–2 користувачі, без ролей (Supabase Auth, один рівень доступу).
- Основна одиниця — **літри**; кг вводяться вручну лише для відображення в Донесенні.
- Період — дати початку/кінця задаються вручну (зазвичай 25→25, інколи 20→25).
- **Жорстка звірка**: сума «Отримано» по авто за видом пального = надходження від постачальника; розбіжність блокує генерацію.
- Генератори: у шляховому листі лише літри (без спідометра/мотогодин).
- Актуальні шаблони — найновіші вкладки (період 25.09.2026–25.10.2026, жовтень).

## Модель даних (Supabase, Postgres + RLS + явні GRANT)
- `fuel_types` — довідник (А-80, А-80 ДЗ, А-92, А-95, ДП-Л В0, ДП-Л В5, ДП-Артика, ДП-З В5, ДП-Л «ДТ.Е»; мастила/рідини з Донесення), група/порядок рядків у документах.
- `vehicles` — 24 одиниці: №, марка, тип, військовий номер, підрозділ, прапор «генератор» (без спідометра), порядок.
- `vehicle_fuels` — які види пального допустимі для кожної одиниці (авто може мати кілька).
- `periods` — звітний період: `date_from`, `date_to`, статус (чернетка/закритий).
- `supplier_receipts` — надходження за період: вид пального, літри, кг (довідково), № накладної/роздавальної відомості.
- `waybills` — шляхові листи: період, авто, вид пального, № листа, літри використано, літри отримано, спідометр початок/кінець (для авто). Кілька на авто за місяць.
- `period_balances` — відкриті залишки (початковий період вводиться вручну; далі = закритий залишок попереднього періоду) по авто × паливо; фактичний замір на кінець (для Відомості заміру).
- `document_settings` — номер в/ч, посади та ПІБ підписантів (командир, начальник логістики, ПММ А4240), текст «Пояснення»; шаблони в Storage.
- Обчислення (чиста TS-логіка, без БД): залишок_кінець = залишок_початок + отримано − використано; агрегати по виду пального для Донесення (прибуло, шляхові листи/робочі листи агрегатів, усього, залишок). Міграції в `supabase/migrations`, SQL-тести в `supabase/tests`.

## Етапи (порядок)
1. **Репозиторій GitHub**: створити repo, README, `docs/` (стек, стиль), гілкування, `.gitignore`.
2. **Скафолд**: Vite+React 19+TS, HashRouter, **Tailwind** (токени теми в конфігу, шрифти @fontsource), ESLint, vitest, Playwright, GitHub Actions (lint/test/build/deploy на Pages).
3. **Supabase**: створити проєкт, міграції схеми, RLS+GRANT, Auth (1–2 користувачі), seed довідників (24 одиниці, види пального з наявних таблиць), SQL-тести.
4. **Ядро розрахунків** (`src/lib/calc`, максимум покриття vitest): ланцюжок залишків між періодами, агрегати, звірка надходжень, валідації (негативний залишок, паливо не з `vehicle_fuels`).
5. **UI**: Період → Надходження від постачальника → Шляхові листи по авто (швидке введення, кілька листів, кілька видів пального) → Звірка/Підсумки (реальний перегляд цифр) → Генерація.
6. **Шаблони документів**: перенести останні вкладки трьох .xls у шаблони. Для xlsx — ExcelJS (збереження форматування/об'єднань), для docx — docxtemplater+pizzip, для PDF — pdf-lib+fontkit (Liberation Serif); попередній перегляд docx-preview.
7. **Тести**: юніт на розрахунки; e2e (Playwright) на повний цикл «період → ввід → звірка → генерація»; звірка згенерованих цифр із жовтневими документами користувача як еталон.
8. **Деплой і міграція даних**: GitHub Pages; опційно імпорт початкових залишків із жовтня 2026.

## Ризики / на що звернути увагу
- У вихідних таблицях є розбіжності між документами (напр. Renault Kangoo 223782 vs 223639 км, 517.7 vs 516.7 л) — звірка в системі їх виявлятиме; еталонні цифри потрібно узгодити з користувачем.
- Назви пального написані по-різному (`ДП Л Євро 5ВО`, `ДП-Л Євро 5-ВО`, `ДП Л Євро 5ВО (ДТ.Е …)`) — нормалізувати через довідник.
- Формат .xls → шаблони потрібно конвертувати в xlsx без втрати об'єднань/форматування.

## Відкриті питання для наступного кроку (не блокують старт)
- Звідки брати «Відомість заміру»: фактичний замір на кінець вводиться окремо від розрахункового?
- Мастила й рідини (олива, ГТЖ, антифриз…) — вводимо в системі чи лишаємо у Донесенні статично/вручну?
- «Витрата по робочих листах агрегата» (напр. 110 л ДП Л В0) — окремий тип запису, відмінний від шляхового листа?
- Підписанти змінюються (в двох .xls різні ПІБ) — редагувати в налаштуваннях?
- Чи потрібен імпорт історичних даних, чи стартуємо з жовтня 2026?

## Перевірка
- `npm run lint && npm test && npm run build` проходять; CI зелений на Pages.
- Ввести жовтневі дані 2026 → згенеровані xlsx/docx/PDF збігаються цифрами з наданими останніми вкладками.
- Негативні сценарії: розбіжність надходжень блокує генерацію; RLS не пускає неавторизованого.
